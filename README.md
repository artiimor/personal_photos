# Personal Photos

A Rails app for storing personal photos. Each user signs up (Devise), uploads their photos from the browser and browses their gallery with thumbnails.

Photos are **not stored in this project**: they live in [file-uploader](../file-uploader), a file server written in Rust (Axum). Rails only keeps the metadata in Postgres (the photo, its owner and the Active Storage blob).

## How it talks to file-uploader

The integration is a custom Active Storage service, `ActiveStorage::Service::FileUploaderService` (`lib/active_storage/service/file_uploader_service.rb`), configured as `file_uploader` in `config/storage.yml`.

- **Per-user keys**: every blob has a key `<user_id>/<uuid>.<ext>` (generated by `CustomDirectUploadsController`), where `<user_id>` is the user's `uid` (a UUID). The user and the file name on file-uploader are derived from it.
- **Endpoints**: `PUT`, `GET` and `DELETE` on `/files/:user_id/:file_name`, plus `GET /files/:user_id/:file_name/metadata` to check whether a file exists (`exist?`).
- **JWT authentication**: every request carries a `?token=` signed with HS256 and `FILE_UPLOADER_JWT_SECRET`, with the claims `sub` (user), `scope` (`upload`, `download`, `delete` or `metadata`), `file_name` and a 5-minute expiry. file-uploader verifies it with its own `JWT_SECRET`, so **both secrets must match**.
- **Direct upload**: the browser uploads the file straight to file-uploader using the signed URL generated by Rails, so the bytes never go through the app.
- **Thumbnails**: the `:thumb` variant (WebP, resized to fit within 300x300 keeping its aspect ratio) is marked as `preprocessed`, so it is generated in the background by Sidekiq when the photo is uploaded. Rails processes it with libvips and stores it back in file-uploader. `GET /photos/:id/thumb` redirects to its signed URL.
- **Errors**: file-uploader responses are mapped to Active Storage errors:
  - 404 → `FileNotFoundError`, except in `exist?` (returns `false`) and `delete` (does nothing, so deleting is idempotent).
  - 422 → `IntegrityError`.
  - 401/403, any other status code and network failures (server down, timeout, DNS) → `Error`. The controller rescues them and responds with a 422.

### Known limitations

- `delete_prefixed` does nothing, so deleting a photo does not delete its variants from file-uploader.
- `download_chunk` downloads the whole file and then slices it, because file-uploader does not support `Range` headers yet.

## Requirements

- Docker and Docker Compose
- file-uploader running on the host, listening on port `3050`

## Running with Docker

1. Create `.env` from the example and adjust the values:

   ```sh
   cp .env.example .env
   ```

   | Variable | Purpose |
   | --- | --- |
   | `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Database credentials |
   | `DATABASE_URL`, `REDIS_URL` | Connections to the `db` and `redis` containers |
   | `FILE_UPLOADER_URL` | file-uploader URL as seen from the container (defaults to `http://host.docker.internal:3050`) |
   | `FILE_UPLOADER_PUBLIC_URL` | Optional. file-uploader URL as seen from the browser (e.g. `http://localhost:3050`). Falls back to `FILE_UPLOADER_URL` if unset |
   | `FILE_UPLOADER_JWT_SECRET` | Secret used to sign the tokens. Must match file-uploader's `JWT_SECRET` |

2. Start file-uploader with the same secret. For the browser to be able to upload files, its `ALLOWED_ORIGINS` must include `http://localhost:3000`.

3. Start the app:

   ```sh
   docker compose up --build
   ```

   This starts the following services:

   | Service | What it does |
   | --- | --- |
   | `web` | Rails on http://localhost:3000 (runs `db:prepare` on startup) |
   | `css` | `tailwindcss:watch` to rebuild the styles |
   | `sidekiq` | Background jobs |
   | `db` | Postgres 17 (port `5432`) |
   | `redis` | Redis 7 |

   The code is mounted as a volume, so changes show up without rebuilding the image. `--build` is only needed when the `Gemfile` changes.

4. Open http://localhost:3000, sign up and upload a photo.

## Tests

The tests use RSpec and stub the calls to file-uploader, so it does not need to be running:

```sh
docker compose --env-file .env.test run --rm -e RAILS_ENV=test web \
  bash -c "bin/rails db:prepare && bundle exec rspec"
```

`--env-file .env.test` only fills in the `${...}` variables in `docker-compose.yml` (`DATABASE_URL`, `REDIS_URL`), so the tests use the test database. The rest of the container's variables, such as `FILE_UPLOADER_JWT_SECRET`, still come from `.env`.
